```cpp
template <class Msg, class Fill>
void publishRealtime(
    const std::shared_ptr<realtime_tools::RealtimePublisher<Msg>>& pub,
    Fill&& fill)
```

## 29. 助手 · 2026-09-28T12:15:02 UTC

对，你的理解是对的。若约定 `base2odom` 表示“把 **base 坐标**转换成 **odom 坐标**”，记作 \(^{odom}T_{base}\)，那么它的旋转矩阵

\[
^{odom}R_{base}
=
\begin{bmatrix}
| & | & |\\
^{odom}\mathbf e_{x,base} & ^{odom}\mathbf e_{y,base} & ^{odom}\mathbf e_{z,base}\\
| & | & |
\end{bmatrix}
\]

三列就是 **base 的三个基向量在 odom 系下的表示**。

对于一个点，还要加上 base 原点在 odom 下的位置：

\[
^{odom}\mathbf p
=
^{odom}R_{base}\,^{base}\mathbf p
+
^{odom}\mathbf t_{base}
\]

对于角速度、加速度这类**方向向量**，只做旋转，不加平移：\(\,^{odom}\mathbf v=\,^{odom}R_{base}\,^{base}\mathbf v\)。

对应 ROS TF，`lookupTransform("odom", "base_link", ...)` 返回的正是这个 **base → odom** 变换。因此按你提出的命名约定，叫 `base2odom` 很合适；当前代码里的 `odom2base` 名称确实容易反着读。

### 2. `linear_acc_base`：用了方向不适用的动态旋转

[当前代码](/home/nesc/catkin_ws/src/rm_controllers/rm_chassis_controllers/src/bipedal_wheel/ros/controller.cpp:164) 用 `odom2imu.inverse()` 去旋转 `acc`。按 ROS 的 IMU 约定，加速度和角速度都**以 IMU 自身坐标系表达**；姿态四元数则描述 IMU 相对其参考世界系的方向。[ROS REP 145](https://ros.org/reps/rep-0145.html) 因此，要把 `acc_imu` 表示到 base 系，应使用固定的 **IMU → base** 旋转，即 `imu2base_tf_.getBasis()`。当前的逆姿态随车体朝向变化，即使 IMU 与 base 完全同轴，车体仅改变偏航角也可能改变算出的所谓 `linear_acc_base`。

```cpp
const tf2::Vector3 acc_imu(acc.x, acc.y, acc.z);
const tf2::Vector3 acc_base = imu2base_tf_.getBasis() * acc_imu;
```

这里原代码调用的 `tf2::doTransform(geometry_msgs::Vector3, ...)` **本身只应用旋转**，见[本机实现](/opt/ros/noetic/include/tf2_geometry_msgs/tf2_geometry_msgs.h:959)；错误在于传给它的是 `odom2imu.inverse()`，而非 IMU → base 的静态变换。修复后的 base 系 `x` 分量会进入[速度估计器](/home/nesc/catkin_ws/src/rm_controllers/rm_chassis_controllers/include/rm_chassis_controllers/bipedal_wheel/core/bipedal_wheel_core_impl.h:288)。

还有一个物理含义需要分清：上述最小修复得到的是**在 IMU 安装点测得、用 base 坐标轴表达的加速度读数**。按 REP 145，加速度计报告的是包含重力效应的 *specific force*。如果估计器真正需要“base 原点的无重力线加速度”，还必须另行处理重力，并考虑 IMU 安装偏移带来的旋转加速度项；仅旋转坐标轴不足以得到那个量。[ROS REP 145](https://ros.org/reps/rep-0145.html)

问题的根源是：**这两个 API 虽然都接收名为 `Vector3` 的类型，却赋予它不同的变换语义。**

设 `imu2base_tf_` 为 IMU → base 的变换，旋转为 \(R\)，平移为 \(t\)：

- **点的位置**需要 \(p_{base}=Rp_{imu}+t\)。
- **角速度**只需换一组坐标轴：\(\omega_{base}=R\omega_{imu}\)。同一刚体上，IMU 装在什么位置不会改变刚体的角速度；它只可能改变线速度和线加速度。

当前 [catkin_ws 的代码](/home/nesc/catkin_ws/src/rm_controllers/rm_chassis_controllers/src/bipedal_wheel/ros/controller.cpp:139) 把角速度包装成 `tf2::Vector3`，再调用 `tf2::Transform * Vector3`。该[运算符的实现](/opt/ros/noetic/include/tf2/LinearMath/Transform.h:90)是 **\(R\omega+t\)**，相当于把角速度当成点的位置来变换。这在量纲上也不成立：它把以**米**表示的安装偏移加到了以 **rad/s** 表示的角速度上。

**最短的判别办法**：复现时同时看 `pid_follow/state` 的输出、`pid_yaw_vel/state`、`legged_chassis_status.d_yaw`、左右轮实际力矩、`lqr_status` 和 `unstick`。若 FOLLOW 输出先左右摆，查云台与目标帧；若目标稳定而轮力矩贴近 ±3.58 N·m，优先处理偏航力矩余量和 PID；若 `x_dot` 或 `unstick` 同步跳动，优先修加速度变换与估计。没有运行数据前，我不会把 PID 或 MPC 权重判成已证实的根因。
